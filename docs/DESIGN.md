# Metanomic 0.2 구현 명세

## 운영 경계

중앙 운영형이며 게임의 가격·보상 대상·아이템 지급 보고를 신뢰한다. 게임은 관리자 승인으로 등록한다. 기본 배분과 판매 수입은 인출 가능한 게임 예산으로 합친다. 이용자 결제와 운영자 인출은 각 지갑의 명시적 서명이 필요하다. 게임 자격증명은 운영자 인출 권한을 가지지 않는다.

로컬 EVM과 Saigon은 같은 API와 EVM 어댑터를 사용하고 배포 설정으로 구분한다. 비 EVM 구현, 브리지, 자산 이전, 실제 돈으로 토큰 판매는 구현 범위에서 제외한다. 다른 배포의 잔액은 합산하지 않는다.

## 권한과 계약 회계

### 관리자 초기 설정

배포는 관리자 계정의 로그인 지갑으로 서버의 계약 관리자 주소만 등록한다. 설치자는 배포가 출력한 일회용 초기 설정 코드(해시만 `admin_setup`에 저장)와 자기 지갑의 소유 확인 서명(`admin-setup` challenge)으로 관리자 로그인 지갑을 등록하고 바로 관리자 세션을 받는다. 코드 검증·지갑 등록·코드 소비·세션 발급은 같은 DB 거래이며, 다른 계정에 연결된 지갑이면 코드를 소비하지 않고 거절한다. 설정이 끝나기 전에는 포털이 일반 로그인을 표시하지 않는다. 서버 셸에서 새 코드를 발급하면 이전 코드는 무효가 된다.

### 운영자 신청

운영자는 지갑으로 가입한 player가 신청하고 관리자가 승인한다. 신청은 승인 지갑의 소유 확인 서명(`operator-wallet` challenge, 5분·1회)을 포함하며, 다른 계정에 연결된 주소와 관리자·중계·정산 계약 주소는 거절한다. 계정당 검토 중 신청은 하나다. 승인 시 같은 DB 거래에서 계정 역할을 operator로 바꾸고 승인 지갑을 기록한다. 반려는 사유를 남기며 재신청할 수 있다. 사용이 중지된 계정(`disabled_accounts`)은 기존 세션이 무효가 되고 새 세션을 받을 수 없으며 거래 기록은 유지한다.

### 게임 등록과 공개

운영자는 자기 계정으로 게임 ID·이름·소개·장르·실행 URL을 신청한다. 운영자와 운영 지갑은 로그인 계정에서 결정하며 요청에서 다른 운영자를 지정할 수 없다. 관리자 승인 후 계약 등록을 접수하고, 계약 최종 확정과 함께 신청을 승인 상태로 바꾼다.

```text
PENDING → REGISTERING → APPROVED
   ↓           ↓
REJECTED      FAILED
   ↓           ↓
PENDING     REGISTERING (관리자 재시도)
```

반려는 계약 제출 전의 PENDING에서만 가능하고 사유를 저장한다. 반려된 신청의 게임 ID는 해당 운영자만 재신청할 수 있다. 통신 오류로 결과를 모르는 등록은 재조회하며, 확실히 실패한 등록만 새 작업으로 재시도한다. 중복 승인 요청은 기존 작업을 반환한다.

공개 `GET /games`는 최종 확정된 활성 게임의 공개 정보만 반환한다. 이용자 카드는 이 응답으로 생성하고 등록된 실행 주소를 연다. 운영 중지 확정 후에는 카탈로그에서 제외한다. 운영자 목록은 본인 소유 게임으로 제한하며 중지된 게임도 관리할 수 있다. API 자격증명은 등록 승인 이후에 발급한다.

`game_registrations`에 신청·심사·작업 연결을, `game_profiles`에 게임 소개·장르·실행 주소를 저장한다. 실행 주소는 사용자에게 공개되는 http(s) URL이며 서버에서 가져오지 않는다. 기존 예제 게임 데이터는 DB 초기화와 재시작 때 누락된 소개만 보완한다.

### 자금과 실행 권한

`CommonCredit`는 ERC-20, ERC-2612, 발행 상한, 관리자 발행 권한을 구현한다. 소수점은 6자리이며 최초 공급량·상한은 배포 설정이다. 보상에 따른 자동 발행은 없다.

관리자는 `POST /issuances`로 상한 안에서 추가 발행한다. 대상은 네트워크 보유분 또는 운영자 승인 지갑이다. 보유분 발행은 관리자 지갑의 `mint → approve → fundReserve` 세 작업이며, 앞 작업이 최종 확정·성공한 뒤에만 다음 작업을 큐에 넣는다. 운영자 지갑 발행은 `mint` 한 건이다. 상한 검사는 확정 블록의 총발행량에 아직 확정되지 않은 발행 수량을 더해 판단한다. 소각 기능은 없다.

`Settlement`의 관리자와 중계 지갑은 다르다. 등록 게임의 운영자 주소는 첫 등록 후 변경할 수 없다. 계약의 게임 활성 상태는 등록 승인 때 켜서 기록하고 이후 바꾸지 않는다. 운영 중 켜기·끄기는 포털 DB(`games.active`)에서 즉시 반영하며, API가 꺼진 게임의 연결 코드·배분·보상·주문·새 결제 승인을 거절한다. 기존 지급·환불·인출은 허용한다. 계약에서 이미 꺼진 게임은 포털에서 다시 켤 수 없다. 관리자는 별도 동작으로 계약에 중지·재개를 기록할 수 있다(`POST /games/{id}/chain-state`, `registerGame` 거래). 중지 기록이 확정되면 포털도 끄고, 재개 기록은 포털 상태를 바꾸지 않는다. 같은 게임의 기록이 처리 중이면 새 기록을 거절한다. 꺼진 게임은 끝나지 않은 결제와 처리 중인 거래가 없을 때 포털에서 삭제할 수 있다. 삭제는 게임·소개·자격증명·계정 연결·신청·예산 캐시를 지우고 결제·보상·감사 기록과 계약의 장부는 남긴다.

| 실행           | 계약 검증                                                     |
| -------------- | ------------------------------------------------------------- |
| 추가 발행      | 토큰 관리자 발행 권한, 발행 상한                              |
| 보유분 충전    | 관리자 권한과 실제 토큰 수령                                  |
| 기본 배분      | 관리자 권한, 배분 ID 미사용, 활성 게임, 충분한 보유분         |
| 보상           | 중계 권한, 보상 ID 미사용, 활성 게임, 충분한 게임 예산        |
| 예치           | 예치 의도 서명, 실제 토큰 수령, 대상 게임·정산 계약 고정      |
| 인출           | 해당 운영자의 예산 변경 서명, 금액·수령 주소·유효기간·nonce   |
| 결제           | 결제 내용 서명, 토큰 주소·금액·게임·주문 고정, 실제 토큰 수령 |
| 지급 시작·완료 | 중계 권한과 결제 상태 전이                                    |
| 일반 환불      | 중계 권한, PAID 상태, 원래 지불자로 반환                      |
| 예외 환불      | DELIVERY_CLAIMED 상태, 운영자와 고정된 복구 관리자 공동 서명  |

중계 지갑의 가스는 관리자 지갑에서 충전한다. 충전은 `fundRelayer` 작업(RON 단순 송금)으로 다른 관리자 거래와 같은 서명 직렬화·재전송·복구를 따른다. 작업 처리기는 1분마다 중계 지갑 잔액을 확인해 기준치 미만이고 진행 중인 충전이 없으면 충전을 큐에 넣으며, 관리자 지갑의 최소 유지분과 송금 수수료를 넘는 양만 보낸다. 관리자가 수동으로 요청한 충전도 같은 유지분 규칙을 적용한다.

항상 `balance >= reserve + totalBudgets + totalEscrow`를 유지한다. 보관금은 인출·보상에 사용하지 않는다. 일반 토큰 직접 전송으로 생긴 차액을 예산으로 편입하지 않는다.

## 서명 규격

로그인은 SIWE(ERC-4361)의 사이트 scheme·domain·URI, 체인, 지갑 주소, 무작위 nonce, 발급·만료 시각, 요청 ID를 포함한다. 서버가 저장한 원문만 검증하며 요청에서 로그인 대상 계정이나 역할을 받지 않는다. challenge는 5분 동안 한 번만 소비하고 세션은 발급 시점부터 최대 8시간이다. 로그인과 기존 계정의 로그인 지갑 등록은 서로 다른 kind·문구·소비 경로를 사용한다.

`login_wallets`는 대소문자와 무관한 EVM 주소를 계정에 연결한다. 기존 관리자·운영자 승인 지갑과 이용자의 수령 지갑도 소유 계정을 해석하는 데 사용한다. 여러 계정으로 해석되는 주소는 거절한다. 새 주소는 player만 생성하며 관리자·운영자 권한을 요청으로 지정할 수 없다. 기존 계정에 새 로그인 지갑을 추가할 때는 해당 계정 세션과 등록 지갑의 서명을 모두 요구한다. 계정 병합은 하지 않는다. 로그인 지갑 등록은 수령 주소와 계약 승인 주소를 변경하지 않으며, 기존 수령 지갑 변경은 기존 소유 확인 API로 처리한다.

일반 개인키 지갑의 서명은 서버에서 검증하며 로그인에 RPC 조회·거래 제출을 요구하지 않는다. 계약 지갑은 EIP-1271 검증을 추가하기 전까지 지원하지 않는다. 로그인은 결제·인출 권한 서명을 대신하지 않는다.

식별자는 계약에서 `keccak256(UTF8(id))`로 표현한다. 금액은 `uint256` 최소 단위이다. API의 소수 문자열은 부동소수점 없이 변환한다. 음수·0·지수 표기·초과 정밀도·오버플로를 거절한다.

정산 서명의 EIP-712 도메인은 `name=Metanomic Settlement`, `version=1`, 실제 chain ID와 정산 계약이다.

```text
Payment(bytes32 paymentId,bytes32 gameId,address payer,address token,uint256 amount,bytes32 orderHash,uint256 nonce,uint256 validUntil)
BudgetAction(bytes32 actionId,bytes32 gameId,address owner,address recipient,uint256 amount,uint256 nonce,uint256 validUntil,bool withdrawal)
Resolution(bytes32 paymentId,bytes32 evidenceHash,uint256 validUntil)
Order(string orderId,string sku,string name,uint256 quantity)
```

`orderHash`는 Order의 EIP-712 구조체 해시이다. 토큰 사용 승인은 Common Game Credit 토큰의 별도 ERC-2612 도메인을 사용하고, spender는 정산 계약이다. 결제·예치의 업무 승인 없이 permit만으로 자금을 이동할 수 없다. 선제출된 permit은 허용된 allowance로 진행하며, 동시 permit nonce 충돌은 같은 결제의 승인 재제출로 복구한다. 일반 개인키 EVM 지갑만 지원한다.

지갑 연결 메시지는 서비스 origin·이용자·주소·체인·목적·무작위 nonce·5분 만료에 묶는다. 계정 연결 코드는 대상 게임과 이용자에 묶고 5분간 한 번만 교환한다. 검증 및 소비는 DB 거래로 보호한다.

## 상태와 시간

작업: `QUEUED → PREPARED → SUBMITTED → INCLUDED → FINALIZED`. 결과 불명은 `RECONCILING`, 확실한 실패만 `FAILED`이다.

결제: `CREATED → PROCESSING → PAID → DELIVERY_CLAIMED → COMPLETED`. PAID에서 환불하면 REFUNDED로, 미결제의 확정된 만료는 EXPIRED로 간다. 지급 시작 이후는 자동 환불하지 않는다.

| 설정                     |                       로컬 |                           Saigon |
| ------------------------ | -------------------------: | -------------------------------: |
| 서명 유효기간            |                      900초 |                           3600초 |
| 수령 이후 지급 시작 기한 |                      900초 |                           3600초 |
| 확정 기준                | 제어 가능한 로컬 최신 블록 | RPC finalized와 영수증 블록 일치 |

현재 체인의 최신 블록 시각으로 서명 만료를 계산한다. 최종 확정이 지연된 과거 블록 시각을 사용하지 않는다. 지급 시작 기간은 계약의 immutable `claimWindow`이며 결제 수령 블록 시각에 더한다. 만료 주문을 최종 판정할 때는 확정 체인 시각을 사용한다.

지불자는 PAID에서 즉시 환불을 요청할 수 있다. 지급 시작과 먼저 체인에 반영된 전이만 성공한다. 지급 시작 기한 경과 후에는 신규 지급 시작을 거절하고 서버가 환불을 접수한다. 화면을 닫는 행위는 이미 발급한 서명을 철회하지 않는다.

게임은 지급 시작 확정 후에만 아이템을 생성한다. 지급 시작 이후 예외 환불은 게임 DB의 영속 지급 금지 잠금, 미지급 확인, 두 승인에 의존한다. 불명확한 지급은 계속 복구 대기로 둔다.

## 영속성·예약·중복

요청 키는 인증 주체·논리 API 경로·경로 매개변수에 묶는다. 검증된 요청을 키 정렬한 정규 JSON으로 해시한다. 같은 키나 업무 참조에 다른 내용이면 409다.

| 업무        | 유일 제약                                    |
| ----------- | -------------------------------------------- |
| 보상        | gameId + rewardRef                           |
| 주문        | gameId + orderId                             |
| 기본 배분   | gameId + period + weekly                     |
| 추가 배분   | gameId + period + additional + allocationRef |
| 추가 발행   | issuanceRef                                  |
| 게임 계정   | gameId + gamePlayerId, gameId + playerId     |
| 아이템 지급 | 게임 DB의 paymentId                          |

업무 유일성은 배포 ID와 무관하게 유지한다. 작업마다 배포 설정, 수령 지갑, 금액, 서명 내용을 고정한다. 등록된 배포 ID의 설정을 덮어쓰지 않는다.

보상과 인출은 SQLite BEGIN IMMEDIATE에서 예약한다. 같은 API를 통한 인출은 예약을 제외한다. 예약은 체인 잠금이 아니며 접수는 지급 보장이 아니다. 작업 성공·확실한 실패에서만 예약을 해제한다. 불명확하면 유지한다.

서명 거래 원문·해시·nonce를 전송 전에 저장한다. 중계 지갑별 제출을 직렬화한다. 재시작 시 모든 시도와 업무 처리 기록을 조회하고 같은 거래를 우선 재전송한다. 수수료 대체는 같은 nonce·같은 호출 내용으로 생성하며 승리한 해시를 추적한다. 미확정 재구성은 포함을 되돌리고 같은 업무를 재조회한다.

작업 처리기는 같은 서명 지갑의 앞선 거래가 블록에 포함되면 다음 거래를 제출한다. 최종 확정은 기다리지 않으므로 처리량이 체인의 확정 지연(Saigon에서 수십 분)에 묶이지 않는다. 업무 결과 반영·예산 갱신·예약 해제는 계속 최종 확정 후에 한다. 미확정 재구성으로 앞선 거래가 사라지면 저장된 같은 서명 원문을 nonce 순서대로 다시 보내며, 뒤 거래는 앞 거래가 다시 포함될 때까지 대기한다. 앞선 거래가 아직 포함되지 않았거나 결과 불명이면 다음 거래를 보내지 않는다.

확정 이벤트 적재·게임 outbox 생성·체인 커서 저장은 같은 DB 거래이다. 커서가 지연돼도 오래된 PAID 이벤트로 현재 완료 상태를 덮어쓰지 않는다. 작업 결과 반영·예산 갱신·예약 해제도 같은 DB 거래이다. 예산 캐시가 원래 기준 블록과 다르면 복구하고 audit와 게임 이벤트를 남긴다.

게임 서버는 이벤트 커서와 미완료 결제 전체 순회를 함께 사용한다. 아이템과 지급 기록은 게임 DB의 같은 거래에 저장한다. 완료 통지가 유실돼도 추가 아이템 없이 재통지한다.

SQLite와 프로세스 잠금은 단일 서버를 위한 것이다. 다중 작업자 운영은 별도 분산 잠금·nonce 관리·DB 전환이 필요하다.

지속 실행하는 로컬 Anvil은 5초 간격으로 채굴하고 30초마다 상태를 저장한다. 과거 상태의 디스크 캐시는 128개로 제한하며 메모리 캐시는 Anvil의 제한을 따른다. 현재 상태와 블록·거래 기록은 유지하고, 최근 과거 상태는 재시작 후 예산 캐시 대조에 사용한다. 과거 상태를 무기한 보장하는 아카이브 모드는 아니다. 저장 파일이 커지는 것을 방지하기 위해 모든 과거 상태를 2초마다 덤프하지 않는다. 정상 종료는 실제 Anvil 프로세스가 저장을 끝낼 때까지 기다린다. 강제 종료·전원 차단까지 DB와 체인의 원자적 영속성을 보장하지 않는다.

외부 RPC 이벤트 조회는 기본 200블록씩 진행한다. 배포 설정의 `maxLogBlockRange`로 더 작은 범위를 지정할 수 있다. 이벤트 색인 오류는 진행 중인 거래의 확정 확인과 결제 기한 복구를 중단시키지 않는다. 색인 커서는 실패 시 전진하지 않으며, 오류는 관리자 화면과 smoke 보고서에 남긴다.
